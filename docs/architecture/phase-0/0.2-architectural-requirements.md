# Shadow : Helix Nebula (SHN)
## Phase 0.2: Architectural Requirements Specification

> **Authoritative Specification Notice**: This document establishes the production-grade, technology-agnostic architectural requirements for Shadow : Helix Nebula (SHN). Formulated directly upon the foundational baselines of Phase 0.1, this specification defines the functional, non-functional, security, operational, and governance requirements governing all future engineering phases. Every requirement is formulated to be testable, unambiguous, and implementation-neutral where concrete technologies remain deferred.

---

# 1. Introduction & Context

### 1.1 Purpose & Scope
This document specifies the architectural requirements for Shadow : Helix Nebula (SHN), a production-oriented, extensible cybersecurity operations and security engineering platform functioning as a unified security control plane. 

### 1.2 Baseline Continuity
All requirements specified herein derive directly from the foundational invariants, philosophical principles, and architectural models established in:
- [Phase 0.1 Specification: Product Identity & Purpose](file:///c:/DESK/Desktop/FOLDERS/Projects/shadow-helix-nebula/docs/architecture/phase-0/0.1-product-identity-and-purpose.md)

### 1.3 Requirement Conventions & Structure
Each requirement is assigned a deterministic identifier and structured as follows:
- **Statement**: Normative requirement using RFC 2119 keywords (**SHALL**, **SHALL NOT**, **SHOULD**, **MAY**).
- **Rationale**: The engineering justification rooted in Phase 0.1 architecture.
- **Verification / Acceptance Criterion**: Testable, objective condition required to validate compliance.

# 2. Functional Requirements (FR)

### 2.1 Workspace & Tenancy Management
- **FR-WKS-001 (Workspace Boundary)**: The platform **SHALL** provide logical isolation of all operational data, targets, workflows, findings, evidence, and logs within a dedicated Workspace container.
  - *Rationale*: Prevents cross-contamination of client data and operational state.
  - *Verification*: Data queries executed within Workspace $A$ must deterministically return zero records belonging to Workspace $B$.
- **FR-WKS-002 (Hierarchical Organization)**: The platform **SHALL** support a multi-tiered hierarchy mapping Organizations to multiple Workspaces, and Workspaces to multiple Engagements.
  - *Rationale*: Accommodates corporate security departments and consulting firms managing distinct clients and test periods.
  - *Verification*: Administrative APIs must permit creating nested entities with strict foreign key associations and cascading rules.

### 2.2 Asset Ingestion & Inventory
- **FR-AST-001 (Asset Discovery & Tracking)**: The platform **SHALL** ingest, deduplicate, and track targets including IPv4/IPv6 addresses, CIDR subnets, FQDNs, URLs, and cloud resource identifiers.
  - *Rationale*: Provides a normalized inventory for targeted security capabilities.
  - *Verification*: Ingestion of overlapping targets (e.g., single host within previously ingested subnet) must update the existing asset record without creating duplicates.
- **FR-AST-002 (Asset Tagging & Context)**: The platform **SHALL** support user-defined metadata, criticality rankings, environmental tags (production, staging, external, internal), and ownership attributes.
  - *Rationale*: Allows workflow routing and risk prioritization based on asset sensitivity.
  - *Verification*: Assets must be queryable and filterable by dynamic tag expressions.

### 2.3 Capability Abstraction & Resolution
- **FR-CAP-001 (Tool-Agnostic Capability Invocation)**: The platform **SHALL** decouple operational intent from concrete tools by exposing abstract capability interfaces (e.g., `capability:network.port-scan`).
  - *Rationale*: Invariant 3 (Capabilities decoupled from tools) ensures workflow longevity.
  - *Verification*: Changing the active capability provider from Provider A to Provider B must not require modifying the invoking workflow definition.
- **FR-CAP-002 (Dynamic Provider Resolution)**: The platform **SHALL** resolve capability requests to available registered providers based on environment, configuration presets, and availability.
  - *Rationale*: Supports portable execution across varied runtime nodes.
  - *Verification*: Invoking a capability on a node lacking the preferred provider must either cleanly fall back to an authorized alternative provider or fail with a typed diagnostic error.

### 2.4 Workflow Authoring & Orchestration
- **FR-WFO-001 (Directed Graph Model)**: The platform **SHALL** support directed execution graphs containing sequential, parallel, conditional, and iterative nodes.
  - *Rationale*: Real-world security assessments are multi-stage and require cyclic iteration.
  - *Verification*: A workflow graph containing a bounded conditional loop (e.g., repeat probe until port open or max retries reached) must execute deterministically without infinite recursion.
- **FR-WFO-002 (Variable & State Propagation)**: The platform **SHALL** pass strongly typed context and normalized intermediate outputs across connected graph nodes.
  - *Rationale*: Downstream tools rely on discovery data from upstream capabilities.
  - *Verification*: Discovered open ports from a scan node must be automatically accessible as input parameters to a downstream service-probing node.

### 2.5 Task Execution & Worker Supervision
- **FR-EXE-001 (Asynchronous Task Dispatch)**: The platform **SHALL** dispatch workflow tasks asynchronously from the Control Plane to designated execution workers.
  - *Rationale*: Invariant 1 (Control Plane and Execution Plane logical separation).
  - *Verification*: Dispatched execution tasks must run in separate worker processes without blocking Control Plane API responsiveness.
- **FR-EXE-002 (Worker Heartbeat & Supervision)**: The platform **SHALL** continuously monitor execution worker health, task progress, and execution timeouts.
  - *Rationale*: Prevents orphaned processes and frozen tasks from stalling workflows.
  - *Verification*: Simulating a worker process kill must cause the Control Plane to detect worker loss within a configurable threshold and transition the task to a failed or retryable state.

### 2.6 Normalization & Correlation
- **FR-NRM-001 (Output Normalization)**: The platform **SHALL** parse raw, proprietary tool outputs into unified domain schemas representing hosts, ports, services, vulnerabilities, and exposures.
  - *Rationale*: Eliminates vendor lock-in and enables cross-tool data aggregation.
  - *Verification*: Outputs from two distinct port scanners must populate identical relational fields in the normalized port entity table.
- **FR-NRM-002 (Cross-Source Correlation)**: The platform **SHALL** correlate disparate observations against common asset records using canonical network keys.
  - *Rationale*: Synthesizes multi-tool outputs into a singular coherent attack surface view.
  - *Verification*: An asset discovered by passive DNS must be merged with active port scan findings when matching canonical IP/domain records.

### 2.7 Finding Lifecycle Management
- **FR-FND-001 (Finding State Machine)**: The platform **SHALL** manage finding states through a formal lifecycle (Draft $\rightarrow$ Under Review $\rightarrow$ Confirmed $\rightarrow$ False Positive $\rightarrow$ Remediated $\rightarrow$ Closed).
  - *Rationale*: Maintains auditability and professional workflow rigor.
  - *Verification*: Invalid state transitions (e.g., transitioning directly from Draft to Closed without review) must be rejected with validation errors.
- **FR-FND-002 (Risk Rating Taxonomies)**: The platform **SHALL** support industry-standard severity metrics (CVSS v3.1/v4.0, CWE, OWASP Top 10) and custom qualitative ratings.
  - *Rationale*: Adapts to varied client compliance requirements.
  - *Verification*: A finding must calculate baseline CVSS vector strings while permitting operator risk overrides with required justification notes.

### 2.8 Reporting & Archival
- **FR-REP-001 (Multi-Stakeholder Deliverables)**: The platform **SHALL** compile normalized findings, executive summaries, technical details, and raw evidence into structured reports (PDF, HTML, JSON).
  - *Rationale*: Fulfills reporting requirements for executive and technical audiences.
  - *Verification*: The reporting engine must render a deliverable containing both high-level executive charts and technical remediation code blocks.
- **FR-REP-002 (Engagement Archival)**: The platform **SHALL** support locking an engagement into an immutable, read-only state upon completion.
  - *Rationale*: Preserves evidentiary chain-of-custody for historical defense.
  - *Verification*: Any write or update request targeted at an archived engagement must be deterministically rejected by the API.

# 3. Non-Functional Requirements (NFR)

### 3.1 Performance & Latency
- **NFR-PRF-001 (API Response Times)**: Standard Control Plane API endpoints (CRUD operations on metadata, scope, and findings) **SHALL** return responses within $\le 200\text{ ms}$ at the 95th percentile under standard operating load.
  - *Verification*: Automated load testing against core REST endpoints measuring p95 latency.
- **NFR-PRF-002 (Real-Time Telemetry Latency)**: Real-time stdout/stderr log streams emitted by execution workers **SHALL** be delivered to subscribed Experience Layer clients within $\le 500\text{ ms}$ of generation.
  - *Verification*: End-to-end timestamp benchmarking from worker stdout capture to WebSocket client reception.

### 3.2 Scalability & Concurrency
- **NFR-SCL-001 (Concurrent Task Execution)**: The platform architecture **SHALL** support scaling from a single local worker executing 5 concurrent tasks to a distributed cluster executing $\ge 500$ concurrent tasks without architectural modification.
  - *Verification*: Benchmark queue worker throughput across distributed worker nodes.
- **NFR-SCL-002 (Large Target Inventory)**: The database schema and ingestion pipeline **SHALL** support workspaces containing $\ge 250,000$ active asset records without degrading search or query performance by more than $20\%$.
  - *Verification*: Database query performance tests on synthetic datasets containing 250k indexed hosts.

### 3.3 Resource Footprint & Efficiency
- **NFR-RES-001 (Local-First Minimal Footprint)**: In single-operator local mode, core platform services (API, Control Plane, baseline Worker, Relational Store, Cache) **SHALL** be capable of running within $\le 4\text{ GB}$ of RAM.
  - *Verification*: Memory profiling of the local baseline topology during idle and single-scan workloads.

### 3.4 Modularity & Maintainability
- **NFR-MOD-001 (Subsystem Decoupling)**: Subsystems **SHALL** interact exclusively via formal interfaces and strongly typed data transfer objects (DTOs), prohibiting direct shared-memory state mutation.
  - *Verification*: Static architectural linting ensuring zero cyclic module dependencies and zero undocumented inter-package couplings.

# 4. Security & Governance Requirements (SEC)

### 4.1 Identity & Authentication
- **SEC-AUT-001 (Robust Authentication)**: The platform **SHALL** support multi-factor authentication (MFA) and standard enterprise identity protocols (OIDC, SAML 2.0).
  - *Rationale*: Defends access to a high-privilege security control plane.
  - *Verification*: Successful authentication requires validating both password and TOTP tokens; single-factor bypass attempts must fail.
- **SEC-AUT-002 (Cryptographic Session Management)**: Authentication tokens **SHALL** utilize cryptographically signed, short-lived tokens with secure revocation mechanisms.
  - *Verification*: Revoked tokens must be rejected at the API gateway within $\le 5\text{ seconds}$ across all cluster instances.

### 4.2 Authorization & RBAC
- **SEC-RBC-001 (Granular Role-Based Access Control)**: The platform **SHALL** enforce fine-grained permissions across organizational, workspace, and engagement boundaries.
  - *Rationale*: Prevents unauthorized operators from accessing sensitive client data or launching tests.
  - *Verification*: An operator assigned `Analyst` role must be prevented from modifying authorized scope or executing invasive capabilities.
- **SEC-RBC-002 (Least Privilege Execution)**: Worker processes executing external tool binaries **SHALL** run under unprivileged system accounts with dropped OS capabilities (`CAP_SYS_ADMIN` disabled).
  - *Verification*: Inspection of worker runtime process privileges confirming non-root execution and drop of extraneous Linux capabilities.

### 4.3 Cryptography & Secrets Management
- **SEC-CRY-001 (Envelope Encryption for Secrets)**: Target credentials, API keys, and sensitive operational tokens **SHALL** be encrypted at rest using envelope encryption (AES-256-GCM) with key separation.
  - *Rationale*: Prevents plain-text credential leaks in database backups or dumps.
  - *Verification*: Direct inspection of database records must confirm ciphertext storage; decryption must only succeed through authenticated key service calls.
- **SEC-CRY-002 (Mandatory Transit Encryption)**: All inter-component network communication (Client-to-API, API-to-Worker, API-to-Database) **SHALL** mandate TLS 1.3 encryption.
  - *Verification*: Rejection of unencrypted plaintext HTTP or TCP connections across all platform ports.

### 4.4 Auditability & Tamper Resistance
- **SEC-AUD-001 (Immutable Audit Logging)**: Every administrative, operational, scope, and execution event **SHALL** generate an immutable, structured audit log entry containing operator ID, timestamp, IP address, action, and outcome.
  - *Rationale*: Ensures full regulatory accountability and forensic defensibility.
  - *Verification*: Audit records must have append-only database permissions; update or delete operations must be rejected at the database level.

# 5. Authorization & Scope Requirements (SCP)

### 5.1 Scope Specification
- **SCP-DEF-001 (Multi-Dimensional Scope Definition)**: The platform **SHALL** define operational scope across five mandatory dimensions:
  1. *Included Targets*: CIDRs, IPs, FQDNs, URLs.
  2. *Excluded Targets*: Strict exclusion blacklists taking precedence over inclusions.
  3. *Allowed Actions*: Specific capabilities authorized for execution.
  4. *Disallowed Actions*: Specific capabilities explicitly prohibited.
  5. *Time Windows*: Authorized testing hours and calendar intervals.
  - *Rationale*: Codifies complex legal rules of engagement into deterministic machine logic.
  - *Verification*: Scope schema validation must require all five dimensions to be explicitly defined before engagement activation.

### 5.2 Mechanical Scope Gatekeeper
- **SCP-ENF-001 (Pre-Dispatch Scope Verification)**: The Control Plane **SHALL** intercept every execution task and validate its resolved target and capability against active scope rules prior to worker dispatch.
  - *Rationale*: Invariant 6 (Scope is an enforceable security boundary).
  - *Verification*: Attempting to dispatch a task targeting an excluded IP must result in immediate task rejection and a high-severity audit event.
- **SCP-ENF-002 (Target Resolution Enforcement)**: Domain names and hostnames **SHALL** be dynamically resolved to IP addresses at validation time, verifying that resulting IP addresses do not map to excluded assets or cloud provider metadata endpoints (e.g., `169.254.169.254`).
  - *Rationale*: Prevents DNS rebinding and indirect scanning of prohibited cloud infrastructure.
  - *Verification*: Submitting an included domain name that resolves to an excluded internal IP must be blocked by the gatekeeper.

### 5.3 Concurrency & Throttling Enforcement
- **SCP-THR-001 (Rate & Concurrency Limits)**: The platform **SHALL** enforce maximum request rates and maximum concurrent target probes as specified in the engagement scope.
  - *Rationale*: Prevents unintentional Denial of Service (DoS) conditions against target networks.
  - *Verification*: Worker task dispatch must throttle execution to stay strictly within configured packets-per-second or requests-per-second thresholds.

# 6. Workflow & Orchestration Requirements (WF)

### 6.1 Workflow Topology
- **WF-TOP-001 (Directed Graph Representation)**: Workflows **SHALL** be modeled as directed execution graphs comprising capability nodes, control flow nodes, condition evaluators, and human approval gates.
  - *Rationale*: Invariant 4 (Workflows decoupled from providers) and ADR-05.
  - *Verification*: The workflow compiler must validate graph syntax, resolve data dependencies, and produce an executable execution plan.
- **WF-TOP-002 (Support for Cyclic & Iterative Execution)**: The workflow engine **SHALL** support cyclic iteration with mandatory termination criteria (max iterations, timeout, or condition breach).
  - *Rationale*: Enables recursive discovery and adaptive probing while preventing infinite loops.
  - *Verification*: Workflows iterating over newly discovered subdomains must terminate deterministically when no new assets are discovered or when iteration limit $N$ is reached.

### 6.2 Human Approval & Policy Gates
- **WF-GAT-001 (Human-in-the-Loop Interlocks)**: Workflows **SHALL** support Human Approval Gate nodes that pause graph execution until an authorized operator inspects intermediate state and explicitly approves continuation.
  - *Rationale*: Invariant 7 and Principle 9 (Human-in-the-loop control).
  - *Verification*: An invasive scan step placed downstream of an approval gate must remain in `PAUSED_PENDING_APPROVAL` state indefinitely until an authenticated operator submits an approval token.
- **WF-GAT-002 (Risk-Based Automated Gating)**: The workflow compiler **SHALL** automatically inject mandatory human approval gates before executing any capability flagged with an `invasive` or `destructive` risk rating.
  - *Verification*: Workflows attempting to execute an active exploit capability must require explicit operator sign-off regardless of workflow author settings.

# 7. Plugin & Capability Requirements (PLG)

### 7.1 Plugin Manifest & Contracts
- **PLG-MAN-001 (Formal Manifest Declaration)**: Every plugin **SHALL** provide an authoritative, machine-readable manifest declaring its unique identifier, semantic version, capabilities implemented, execution requirements, configuration schema, and permission requests.
  - *Rationale*: Standardizes plugin discovery, validation, and lifecycle management.
  - *Verification*: Attempting to load a plugin with an invalid manifest schema or missing required fields must fail during registration.
- **PLG-MAN-002 (Semantic Versioning & Compatibility)**: Plugins **SHALL** declare platform API compatibility constraints using standard Semantic Versioning ranges.
  - *Verification*: The plugin loader must refuse to activate plugins whose declared engine compatibility does not match the active Control Plane version.

### 7.2 Plugin Sandboxing & Trust
- **PLG-SEC-001 (Cryptographic Signature Verification)**: The platform **SHALL** verify cryptographic signatures of plugin packages against trusted public keys before installation or execution.
  - *Rationale*: Invariant 8 (Plugins operate under explicit trust and permission boundaries).
  - *Verification*: An unsigned plugin or a plugin with an invalid signature must be rejected by the plugin manager in production mode.
- **PLG-SEC-002 (Execution Sandboxing)**: Plugins and their invoked tools **SHALL** execute within isolated sandboxes (containers or restricted process namespaces) with restricted access to host filesystems and local networks.
  - *Verification*: A compromised or malicious tool script attempting to read host `/etc/shadow` or host root filesystem must be denied by OS sandbox policies.

# 8. Workspace & Engagement Requirements (WKS)

### 8.1 Isolation & Data Boundary
- **WKS-ISO-001 (Complete Data Isolation)**: All relational database queries, cache keys, and object storage paths **SHALL** be strictly scoped by `workspace_id`.
  - *Rationale*: Guarantees client confidentiality and multi-tenant security.
  - *Verification*: Automated penetration testing verifying zero horizontal privilege escalation or IDOR vulnerabilities across workspace boundaries.

### 8.2 Engagement Governance
- **WKS-ENG-001 (Temporal Window Enforcement)**: Engagements **SHALL** enforce active start and expiration timestamps; the orchestrator **SHALL NOT** dispatch tasks outside these boundaries.
  - *Verification*: Submitting a task against an engagement where `current_time > expiration_timestamp` must be blocked by the orchestrator.

# 9. Evidence & Provenance Requirements (EVD)

### 9.1 Evidentiary Integrity
- **EVD-INT-001 (Raw Output Immutability)**: The platform **SHALL** capture unmodified stdout, stderr, raw packets, and exit codes from every executed capability and persist them without alteration.
  - *Rationale*: Invariant 5 (Evidence maintains provenance).
  - *Verification*: Comparing raw captured tool output against historical execution logs must show exact byte-for-byte fidelity.
- **EVD-INT-002 (Cryptographic Hashing on Ingestion)**: Every evidence artifact **SHALL** have its cryptographic SHA-256 hash computed immediately upon ingestion and recorded in the structured database.
  - *Verification*: Any post-ingestion tampering with stored artifact bytes must be detected by automated hash verification checks.

### 9.2 Complete Provenance Ledger
- **EVD-PRV-001 (Unbroken Lineage Chain)**: Every finding, normalized asset record, and report excerpt **SHALL** maintain a traceable lineage link to the exact execution run, tool version, plugin, configuration arguments, target, operator, and timestamp that created it.
  - *Rationale*: Section 20 Provenance Model.
  - *Verification*: Given a finding ID, an API call must traverse the lineage graph and return the exact CLI string, tool version, and raw stdout block that evidenced the finding.

# 10. Observability Requirements (OBS)

### 10.1 Structured Telemetry & Tracing
- **OBS-TEL-001 (Structured JSON Logging)**: All platform components **SHALL** emit structured JSON logs containing timestamp, log level, correlation ID, component name, and contextual attributes.
  - *Verification*: Log parsing validation confirming $100\%$ compliance with structured JSON schema.
- **OBS-TEL-002 (Distributed Trace Propagation)**: The platform **SHALL** propagate OpenTelemetry-compliant W3C trace contexts across all API requests, message queues, and worker executions.
  - *Rationale*: Section 23 Observability Foundation.
  - *Verification*: Visualizing an end-to-end trace in an OpenTelemetry APM collector showing the complete path from HTTP API request to worker execution and database commit.

### 10.2 Metrics & Health Monitoring
- **OBS-MET-001 (Prometheus Metrics)**: Platform components **SHALL** expose Prometheus-compatible `/metrics` endpoints tracking task queue depth, execution latencies, worker CPU/memory usage, and error rates.
  - *Verification*: Automated scraping of `/metrics` endpoints validating metric formatting and counter updates.
- **OBS-HLT-001 (Health & Readiness Probes)**: All services **SHALL** provide `/healthz` and `/readyz` endpoints indicating process liveness and external dependency availability.
  - *Verification*: Disconnecting the database must cause `/readyz` to immediately return HTTP 503 while `/healthz` indicates process liveness.

# 11. API & Client Requirements (API)

### 11.1 API-First Principles
- **API-FST-001 (Contract-Driven OpenAPI Specifications)**: All Control Plane endpoints **SHALL** be formally specified in OpenAPI 3.1 contracts prior to client implementation.
  - *Rationale*: Invariant 2 and ADR-11 (API-First architecture).
  - *Verification*: Automated CI pipeline validating that API code implementations match OpenAPI schema contracts without drift.
- **API-FST-002 (Public Endpoint Parity)**: The official Web UI **SHALL NOT** utilize any internal, private, or undocumented APIs; all functionality must be accessible via public, versioned API endpoints.
  - *Verification*: Complete headless execution of an entire assessment lifecycle using only the public REST API and CLI client.

### 11.2 Real-Time Event Streaming
- **API-EVT-001 (Bidirectional Event Streaming)**: The platform **SHALL** support WebSocket or Server-Sent Events (SSE) interfaces for streaming real-time task progress, stdout logs, and state updates to clients.
  - *Verification*: Client subscription tests verifying receipt of live task log chunks with sub-second latency.

# 12. Data & Storage Requirements (DAT)

### 12.1 Structured System of Record
- **DAT-REC-001 (Relational Data Integrity)**: The primary system of record **SHALL** be a relational database (PostgreSQL per ADR-07) enforcing strict foreign keys, transactional ACID compliance, and schema migrations.
  - *Verification*: Attempting to insert orphaned child records (e.g., finding without an asset or engagement) must violate relational foreign key constraints.

### 12.2 Transient State & Messaging
- **DAT-QUE-001 (High-Speed Queue Semantics)**: Transient task queues and pub/sub message brokers (Redis per ADR-08) **SHALL** provide at-least-once task delivery semantics and reliable dead-letter queue (DLQ) handling.
  - *Verification*: Worker crashes during task execution must result in task re-delivery or routing to DLQ after configurable retry exhaustion.

### 12.3 Large Artifact Vault
- **DAT-OBJ-001 (Object Storage Separation)**: Unstructured artifacts (PCAPs, screenshots, raw logs $>1\text{ MB}$) **SHALL** be stored in an S3-compatible object storage layer rather than relational database tables.
  - *Rationale*: ADR-09 prevents database bloat and performance degradation.
  - *Verification*: Relational database backups must remain lightweight while object stores retain binary blobs referenced by URI and SHA-256 hash.

# 13. Extensibility Requirements (EXT)

### 13.1 Schema & UI Customization
- **EXT-CUS-001 (Dynamic Custom Fields)**: Workspaces **SHALL** support operator-defined custom fields and tags attached to assets, findings, and engagements.
  - *Verification*: Custom metadata fields must be queryable via the API and exportable in reports.
- **EXT-CUS-002 (Pluggable Report Templates)**: The reporting engine **SHALL** support user-provided custom report templates utilizing standard templating languages (e.g., Jinja2, HTML/CSS).
  - *Verification*: Rendering a report using a custom corporate branding template must produce conforming deliverables without modifying platform code.

# 14. Reliability & Resilience Requirements (REL)

### 14.1 Fault Tolerance & Crash Recovery
- **REL-FLT-001 (Worker Crash Recovery)**: If an execution worker process crashes or terminates unexpectedly, the Control Plane **SHALL** detect the failure, log the exit state, release concurrency locks, and mark the task as failed or eligible for retry.
  - *Verification*: Sending `SIGKILL` to an active worker must not cause the Control Plane to hang or leave target assets permanently locked.
- **REL-FLT-002 (Graceful Task Cancellation)**: Operators **SHALL** have the ability to trigger an immediate emergency stop on any active task or entire workflow, cleanly terminating worker processes and network connections.
  - *Verification*: Issuing a task cancel API command must terminate remote child processes within $\le 3\text{ seconds}$ and record a cancellation audit entry.

# 15. Usability & Operator Experience Requirements (UX)

### 15.1 Operator Ergonomics
- **UX-ERG-001 (Visual Workflow Graph Builder)**: The Web UI **SHALL** provide an interactive, visual graph editor allowing operators to compose, configure, and inspect directed workflow graphs.
  - *Verification*: Usability testing confirming visual node connection, parameter binding, and real-time syntax validation within the UI.
- **UX-ERG-002 (CLI Full Scriptability)**: The platform CLI **SHALL** provide scriptable, machine-readable output modes (JSON, YAML, quiet) for integration into shell pipelines and automation scripts.
  - *Verification*: Chaining CLI commands via standard UNIX pipes (e.g., `shn asset list --json | jq .`) must execute cleanly without interactive prompts.

# 16. Deployment & Topology Requirements (DEP)

### 16.1 Local-First & Distributed Topology
- **DEP-TOP-001 (Single-Node Local Deployment)**: The platform **SHALL** be fully deployable and operational on a single workstation or laptop with zero mandatory external internet connections.
  - *Rationale*: Invariant 10 and Section 24 Local-First architecture.
  - *Verification*: Deploying SHN in an air-gapped test environment with network interfaces disconnected must result in full functionality for local scanning and analysis.
- **DEP-TOP-002 (Distributed Cluster Topology)**: The platform **SHALL** support scaling out execution workers across multiple independent host machines and networks without altering the central Control Plane code.
  - *Verification*: Registering a remote worker node residing on a separate subnet and dispatching tasks across it from the primary Control Plane.

### 16.2 Runtime Neutrality
- **DEP-RTN-001 (Container & Process Runtime Independence)**: The execution subsystem **SHALL** support running workloads via local host processes or containerized sandboxes via an abstract execution runtime interface.
  - *Rationale*: Invariant 12 and ADR-10.
  - *Verification*: Capability execution must succeed identically whether configured to use the host process runner or the containerized OCI runner.

# 17. AI & Intelligence Constraints (AIC)

### 17.1 Advisory & Non-Autonomous Guardrails
- **AIC-GUA-001 (Mandatory Non-Autonomous Operation)**: AI models and intelligence services **SHALL NOT** possess direct, un-gated authorization to execute security capabilities, modify scope, or alter system configurations.
  - *Rationale*: Invariant 7 (No unrestricted AI execution) and Section 11.
  - *Verification*: Every AI-suggested operational action must be emitted as a pending recommendation requiring explicit human operator approval before task creation.
- **AIC-GUA-002 (Deterministic Scope Filtering of AI Suggestions)**: Any action suggested by an AI model **SHALL** be evaluated by the mechanical scope gatekeeper prior to being displayed as an actionable recommendation to the operator.
  - *Verification*: An AI recommendation targeting an excluded IP address must be intercepted and suppressed by the scope filter, with an explanatory warning logged.

### 17.2 Data Privacy & Sanitization
- **AIC-PRV-001 (Prompt Sanitization & Data Boundary)**: When external or cloud-based AI providers are configured, the platform **SHALL** redact sensitive target credentials, client PII, and internal proprietary keys prior to transmitting prompts.
  - *Verification*: Inspection of outgoing API payloads to external AI endpoints verifying cryptographic hashing or redaction of credential tokens.
- **AIC-PRV-002 (Local Model Support)**: The intelligence subsystem **SHALL** support pluggable local, offline models (e.g., Ollama, vLLM) for high-confidentiality air-gapped operations.
  - *Verification*: Successful execution of finding summarization and report drafting using an isolated local LLM with zero outbound internet traffic.
