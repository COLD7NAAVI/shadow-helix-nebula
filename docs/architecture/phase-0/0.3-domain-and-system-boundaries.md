# Shadow : Helix Nebula (SHN)
## Phase 0.3: Domain & System Boundaries Specification

> **Authoritative Specification Notice**: This document establishes the formal Domain-Driven Design (DDD) bounded contexts, domain entities, system boundaries, dependency constraints, trust zones, and security isolation rules for Shadow : Helix Nebula (SHN). Built directly upon the foundational identity of Phase 0.1 and the testable requirements of Phase 0.2, this specification defines the architectural perimeters and separation of concerns that govern all downstream design, data modeling, API definition, and implementation phases.

---

# 1. Introduction & Context

### 1.1 Purpose
The purpose of this specification is to partition the problem space of SHN into clean, cohesive, and decoupled **Bounded Contexts**, establish strict **System Layer Boundaries**, and declare explicit rules governing **Allowed and Forbidden Dependencies**.

### 1.2 Foundational Invariant Alignment
This specification strictly operationalizes the foundational invariants established in Phase 0.1:
- **Invariant 1**: Control Plane and Execution Plane logical separation.
- **Invariant 2**: Frontend is strictly a presentation layer, not authoritative domain logic.
- **Invariant 3 & 4**: Decoupling of abstract capabilities from concrete tools, and workflows from concrete providers.
- **Invariant 5 & 6**: Cryptographic evidence provenance and mechanical scope enforcement as hard perimeter boundaries.
- **Invariant 7 & 8**: Non-autonomous AI guardrails and sandboxed plugin trust perimeters.
- **Invariant 9 & 10**: Infrastructure neutrality of core domain logic and local-first/distributed-ready topology parity.

# 2. Core Bounded Contexts

SHN is partitioned into eleven cohesive Bounded Contexts, each possessing distinct domain ubiquity, ubiquitous language, models, and boundaries.

```
+---------------------------------------------------------------------------------------+
|                                SHN BOUNDED CONTEXTS                                   |
+---------------------------------------------------------------------------------------+
| 1. Identity & Governance Context      | 2. Workspace & Engagement Context             |
|    (Users, Orgs, Roles, Audit)        |    (Workspaces, Engagements, Assets)          |
+---------------------------------------+-----------------------------------------------+
| 3. Scope Enforcement Context          | 4. Capability & Plugin Registry Context       |
|    (Inclusions, Exclusions, Gatekeeper|    (Capabilities, Providers, Manifests)       |
+---------------------------------------+-----------------------------------------------+
| 5. Workflow & Orchestration Context   | 6. Task Execution & Worker Supervision Context|
|    (Graphs, Nodes, Policy Interlocks) |    (Jobs, Tasks, Workers, Heartbeats)         |
+---------------------------------------+-----------------------------------------------+
| 7. Normalization & Correlation Context| 8. Finding & Vulnerability Management Context |
|    (Parsers, Entity Graph, Merging)   |    (Findings, CVSS, Triage Lifecycle)         |
+---------------------------------------+-----------------------------------------------+
| 9. Evidence Vault & Provenance Context| 10. Assisted Intelligence Context             |
|    (Artifacts, Hashes, Lineage Graph) |     (Model Routing, Context Triage, Redaction)|
+---------------------------------------+-----------------------------------------------+
| 11. Reporting & Deliverables Context  |                                               |
|     (Templates, Compilers, Archival)  |                                               |
+---------------------------------------+-----------------------------------------------+
```

### 2.1 Context 1: Identity & Governance (BC-IAM)
- **Domain Focus**: User authentication, session lifecycles, enterprise tenancy (Organizations), Role-Based Access Control (RBAC), and immutable operational audit logging.
- **Ubiquitous Language**: `User`, `Organization`, `Role`, `PermissionGrant`, `SessionToken`, `AuditEvent`.
- **Primary Responsibility**: Authoritatively verify *who* is acting and whether they hold legitimate authority to access a workspace or perform an administrative operation.

### 2.2 Context 2: Workspace & Engagement (BC-WKS)
- **Domain Focus**: The primary operational container (Workspace), time-bounded assessment campaigns (Engagements), Rules of Engagement (RoE), and target asset inventories.
- **Ubiquitous Language**: `Workspace`, `Engagement`, `Asset`, `AssetIdentifier` (IP, CIDR, FQDN, URL), `OperationalWindow`.
- **Primary Responsibility**: Maintain the authoritative inventory of target environments and encapsulate operational state within isolated client partitions.

### 2.3 Context 3: Scope Enforcement (BC-SCP)
- **Domain Focus**: Enforceable operational boundaries, target validation, CIDR/IP resolution, exclusion blacklists, action whitelists, and rate limits.
- **Ubiquitous Language**: `ScopeBoundary`, `InclusionRule`, `ExclusionRule`, `AllowedAction`, `ScopeGatekeeper`, `ResolutionVerdict`.
- **Primary Responsibility**: Act as an impenetrable mechanical gatekeeper that deterministically evaluates targets and capability requests before any execution task is permitted to leave the Control Plane.

### 2.4 Context 4: Capability & Plugin Registry (BC-CAP)
- **Domain Focus**: Standardized security capability interfaces, tool provider metadata, plugin manifests, sandboxing contracts, and version compatibility matrices.
- **Ubiquitous Language**: `Capability`, `CapabilityContract`, `Provider`, `PluginManifest`, `SandboxedRuntimeSpec`, `PluginSignature`.
- **Primary Responsibility**: Index and resolve abstract security intents to registered tool providers while enforcing plugin integrity and execution specifications.

### 2.5 Context 5: Workflow & Orchestration (BC-WFO)
- **Domain Focus**: Directed execution graphs, node dependencies, variable bindings, conditional branching, human approval gates, and execution policies.
- **Ubiquitous Language**: `WorkflowGraph`, `WorkflowNode`, `TransitionEdge`, `ExecutionPolicy`, `ApprovalGate`, `ExecutionContext`.
- **Primary Responsibility**: Compile declarative workflow specifications into executable task dependency graphs and manage state transitions.

### 2.6 Context 6: Task Execution & Worker Supervision (BC-EXE)
- **Domain Focus**: Asynchronous job queues, task scheduling, worker pool supervision, process heartbeats, stdout/stderr streaming, and runtime isolation.
- **Ubiquitous Language**: `Job`, `Task`, `ExecutionWorker`, `RuntimeAdapter` (Host, Container, MicroVM), `WorkerHeartbeat`, `ProcessExitState`.
- **Primary Responsibility**: Dispatch compiled tasks to isolated workers, supervise execution runtimes, capture raw process streams, and handle worker failures.

### 2.7 Context 7: Normalization & Correlation (BC-NRM)
- **Domain Focus**: Output parsing, data transformation from proprietary tool outputs into standard domain schemas, cross-source entity resolution, and asset correlation.
- **Ubiquitous Language**: `RawOutputParser`, `NormalizedHost`, `NormalizedService`, `NormalizedExposure`, `CorrelationKey`.
- **Primary Responsibility**: Ingest heterogeneous tool outputs and translate them into standardized, deduplicated domain records mapped to canonical assets.

### 2.8 Context 8: Finding & Vulnerability Management (BC-FND)
- **Domain Focus**: Vulnerability identification, CVSS risk scoring, finding lifecycle state machines (Draft $\rightarrow$ Confirmed $\rightarrow$ Remediated), and remediation tracking.
- **Ubiquitous Language**: `Finding`, `VulnerabilityReference` (CVE, CWE), `RiskScore`, `Severity`, `TriageStatus`, `RemediationNote`.
- **Primary Responsibility**: Manage the formal lifecycle of identified security vulnerabilities and link them directly to underlying evidentiary proofs.

### 2.9 Context 9: Evidence Vault & Provenance Ledger (BC-EVD)
- **Domain Focus**: Forensic capture, cryptographic hashing, immutable raw artifact storage, and unbroken execution lineage graphs.
- **Ubiquitous Language**: `EvidenceArtifact`, `SHA256Hash`, `ProvenanceNode`, `LineageEdge`, `CryptographicSeal`.
- **Primary Responsibility**: Guarantee that every observation, finding, and generated deliverable is permanently linked to verified, immutable raw evidence with verifiable execution lineage.

### 2.10 Context 10: Assisted Intelligence (BC-INT)
- **Domain Focus**: Contextual model routing, summarization, finding correlation assistance, natural language querying, prompt redaction, and human authorization interlocks.
- **Ubiquitous Language**: `IntelligenceRequest`, `ModelRouter`, `ContextSynthesizer`, `RedactionFilter`, `AdvisoryRecommendation`.
- **Primary Responsibility**: Provide supervised cognitive assistance to operators while strictly filtering all suggestions through the Scope Gatekeeper and human approval gates.

### 2.11 Context 11: Reporting & Deliverables (BC-REP)
- **Domain Focus**: Document template compilation, executive summaries, technical remediation guides, export pipelines (PDF, HTML, JSON), and engagement archival seals.
- **Ubiquitous Language**: `ReportTemplate`, `ReportDocument`, `ExecutiveSummary`, `RemediationGuide`, `ArchivedEngagementSeal`.
- **Primary Responsibility**: Assemble normalized findings and cryptographic evidence into publishable deliverables and seal completed engagements.

# 4. System Layer Boundaries

SHN enforces strict horizontal and vertical separation across its five system layers:

```
+-----------------------------------------------------------------------+
|                           EXPERIENCE LAYER                            |
|        Web Interface | Desktop Client | CLI | Public REST API         |
+-----------------------------------------------------------------------+
                                   |
                  (Public API Gateway / OpenAPI Contract)
                                   v
+-----------------------------------------------------------------------+
|                            CONTROL PLANE                              |
| BC-IAM | BC-WKS | BC-SCP | BC-CAP | BC-WFO | BC-FND | BC-EVD | BC-REP |
+-----------------------------------------------------------------------+
             |                           |                     |
   (State Read/Write)           (Task Queue / Events)    (Context Data)
             v                           v                     v
+------------------------+   +-----------------------+ +---------------+
|       DATA PLANE       |   |    EXECUTION PLANE    | | INTELLIGENCE  |
| - PostgreSQL (Records) |   | - Task Dispatch Queue | |     LAYER     |
| - Redis (Queues/Cache) |   | - Worker Supervisor   | | - Model Router|
| - Object Store (Blobs) |   | - Isolated Runtimes   | | - Redaction   |
+------------------------+   | - Tool Execution      | | - Approval    |
                             +-----------------------+ +---------------+
```

### 4.1 Boundary 1: Experience Layer Perimeter
- **Boundaries**: Client applications (Web, Desktop, CLI) and third-party API clients operate outside the internal trust perimeter.
- **Rules**:
  - All communication must traverse the Public API Gateway over authenticated, TLS 1.3-encrypted channels.
  - The Experience Layer has **zero** direct access to databases, Redis queues, filesystem storage, or worker processes.
  - All operations are subject to RBAC evaluation and rate limiting.

### 4.2 Boundary 2: Control Plane Perimeter
- **Boundaries**: The central coordination engine containing domain logic, compilation, governance, and state management.
- **Rules**:
  - Authoritative for business rules, scope validation, and state persistence.
  - **SHALL NOT** directly execute external security tools or untrusted scripts.
  - Interacts with the Execution Plane exclusively via asynchronous message queues and decoupled worker APIs.

### 4.3 Boundary 3: Execution Plane Perimeter
- **Boundaries**: Distributed worker nodes, execution runtimes (Host, OCI Containers, Sandboxes), and tool child processes.
- **Rules**:
  - The Execution Plane is an unprivileged execution environment.
  - Workers hold **zero** direct database credentials for the primary relational system of record; state changes are reported back to the Control Plane via message queues or worker callback APIs.
  - Child tool processes must execute within dropped-privilege namespaces with restricted filesystem and network access.

### 4.4 Boundary 4: Data Plane Perimeter
- **Boundaries**: Storage infrastructure (PostgreSQL relational database, Redis message broker/cache, and S3-compatible object storage).
- **Rules**:
  - Accessible only by authorized Control Plane services and designated background queue consumers.
  - Relational tables are partitioned logically by `workspace_id`.
  - Binary object storage stores raw blobs and computes cryptographic hashes; it contains no domain logic.

### 4.5 Boundary 5: Intelligence Layer Perimeter
- **Boundaries**: AI model routing, prompt preparation, response synthesis, and policy evaluation.
- **Rules**:
  - Possesses **zero** direct execution authority.
  - Prompts must pass through the Redaction Filter before leaving the internal boundary to external model providers.
  - All generated recommendations must be intercepted by the Scope Gatekeeper and Human Approval Gate before becoming actionable tasks.

| :--- | :--- | :--- |
| **Experience Layer** | Client presentation, operator ergonomic interactions, input capture, telemetry rendering. | Domain logic, scope validation, permission enforcement, database access, task execution. |

| **Data Plane** | Transactional durability, relational integrity, cache eviction, object storage persistence, hash checking. | Business rule evaluation, scope enforcement, task dispatch decisions. |
| **Intelligence Layer** | Contextual summarization, correlation heuristics, advisory synthesis, prompt redaction. | Direct execution dispatch, autonomous target probing, un-gated configuration modifications. |

# 6. Allowed & Forbidden Dependency Matrix

To ensure modularity and prevent architectural rot, dependencies between Bounded Contexts are strictly governed by the following matrix:

```
+---------------------------------------------------------------------------------------+
|                         BOUNDED CONTEXT DEPENDENCY RULES                              |
+---------------------------------------------------------------------------------------+
| SOURCE CONTEXT       | MAY DIRECTLY CALL / DEPEND UPON        | FORBIDDEN TO CALL     |
+----------------------+----------------------------------------+-----------------------+
| BC-IAM (Identity)    | Data Plane (Users, Roles)              | BC-EXE, BC-CAP, UI    |
+----------------------+----------------------------------------+-----------------------+
| BC-WKS (Workspaces)  | BC-IAM, Data Plane                     | BC-EXE, Direct Tools  |
+----------------------+----------------------------------------+-----------------------+
| BC-SCP (Scope)       | BC-WKS, BC-IAM                         | BC-EXE, BC-INT, Tools |
+----------------------+----------------------------------------+-----------------------+
| BC-CAP (Capabilities)| Data Plane (Manifests)                 | BC-EXE, BC-WKS, UI    |
+----------------------+----------------------------------------+-----------------------+
| BC-WFO (Workflows)   | BC-CAP, BC-SCP, BC-WKS, BC-IAM         | Direct Tool Binaries  |
+----------------------+----------------------------------------+-----------------------+
| BC-EXE (Execution)   | BC-EVD (Raw Artifacts), Queue Broker   | BC-WFO, BC-SCP, DB SQL|
+----------------------+----------------------------------------+-----------------------+
| BC-NRM (Normalize)   | BC-CAP, Data Plane (Normalized Models) | BC-EXE Runtimes, UI   |
+----------------------+----------------------------------------+-----------------------+
| BC-FND (Findings)    | BC-EVD, BC-WKS, BC-NRM                 | BC-EXE, Direct Tools  |
+----------------------+----------------------------------------+-----------------------+
| BC-EVD (Evidence)    | Data Plane (Object Storage, Hashes)    | BC-EXE, UI, BC-INT    |
+----------------------+----------------------------------------+-----------------------+
| BC-INT (Intelligence)| BC-SCP, BC-FND, BC-WKS                 | Direct Task Dispatch  |
+----------------------+----------------------------------------+-----------------------+
| BC-REP (Reporting)   | BC-FND, BC-EVD, BC-WKS, BC-IAM         | BC-EXE, Direct Tools  |
+----------------------+----------------------------------------+-----------------------+
```

### 6.1 Explicit Prohibitions
1. **No Circular Context Coupling**: Bounded Contexts must form a Directed Acyclic Graph (DAG) of dependency. `BC-EXE` must never call into `BC-WFO`.
2. **Execution Worker DB Isolation**: Execution workers in `BC-EXE` **SHALL NOT** establish direct connections to the primary PostgreSQL database. All state must be communicated via the task queue or Control Plane worker callback API.
3. **Frontend Independence**: The Experience Layer **SHALL NOT** import internal domain services directly. Communication is restricted to public API contracts.

# 7. Trust & Authorization Boundaries

```
[Untrusted Client Zone]
         |
         | (1. User Auth: OIDC / MFA / Session Token over TLS 1.3)
         v
+-----------------------------------------------------------------------+
| [TRUST ZONE A: Control Plane Core]                                    |
| Identity Verification -> RBAC Evaluation -> Scope Gatekeeper          |
+-----------------------------------------------------------------------+
         |
         | (2. Worker Auth: Mutual TLS / Short-Lived HMAC Tokens)
         v
+-----------------------------------------------------------------------+
| [TRUST ZONE B: Execution Plane / Workers]                             |
| Unprivileged Worker Daemon -> Task Verification                       |
+-----------------------------------------------------------------------+
         |
         | (3. Sandbox Boundary: Container / cgroup / dropped caps)
         v
+-----------------------------------------------------------------------+
| [TRUST ZONE C: Sandboxed Tool Process]                                |
| Concrete Tool Binary / Script -> Network Target Probing               |
+-----------------------------------------------------------------------+
```

### 7.1 Trust Zone A (Control Plane Core)
- **Trust Level**: Highly Trusted.
- **Invariants**: Holds master keys for envelope encryption, coordinates database state, validates scopes, and emits audit records.

### 7.2 Trust Zone B (Execution Worker Daemon)
- **Trust Level**: Moderately Trusted.
- **Invariants**: Connects via mTLS to the task queue, verifies that task tokens are signed by the Control Plane, and manages execution runtimes. Cannot alter database records or bypass scope.

### 7.3 Trust Zone C (Sandboxed Tool Process)
- **Trust Level**: Untrusted / Hostile.
- **Invariants**: Tool binaries (e.g., third-party scanners, exploit scripts) execute in isolated containers or dropped-privilege namespaces. They cannot read host secrets, access Control Plane internal ports, or communicate with sibling worker processes.

# 8. Security Isolation Rules

### 8.1 Multi-Tenant Organization Segregation
- Organizations represent distinct commercial entities or clients.
- All database queries must enforce tenant isolation at the query planner level.
- Encryption keys for secrets are compartmentalized per Organization; a compromise of Org $A$'s key material provides zero cryptographic advantage against Org $B$.

### 8.2 Workspace Data Boundaries
- Workspaces within the same Organization are logically isolated.
- Targets, scan jobs, raw evidence, and vulnerability findings are strictly foreign-keyed to `workspace_id`.
- Cross-workspace data sharing requires an explicit administrative export/import action that is immutably logged in the audit ledger.

### 8.3 Execution Workload Sandboxing
- Tool processes must never run as root/superuser.
- Filesystem mounts for execution containers must be read-only except for a dedicated ephemeral scratch directory.
- Container network routing is constrained strictly to the authorized target interfaces; local host management ports (e.g., `localhost:5432`, `localhost:6379`) are blocked.

# 9. External Integration Boundaries

SHN explicitly demarcates the interface boundaries between the platform and external systems:

### 9.1 Target Network Boundary
- The perimeter between SHN execution workers and target infrastructure.
- Governed entirely by the **Scope Enforcement Context (BC-SCP)**.
- Only network packets generated by authorized capabilities targeting validated assets are permitted to cross this boundary.

### 9.2 Tool & Binary Provider Boundary
- The interface between execution workers and underlying CLI tools.
- Governed by the **Capability & Plugin Registry Context (BC-CAP)**.
- Interactions occur via standard POSIX process semantics (stdin, stdout, stderr, exit codes, process signals).

### 9.3 External AI & Model Provider Boundary
- The interface between the Intelligence Layer and cloud-hosted LLM APIs (OpenAI, Anthropic, Google) or local models (Ollama).
- Governed by the **Redaction Filter**; raw target credentials, tokens, and PII are redacted prior to payload dispatch.

### 9.4 Enterprise SIEM / Ticketing Boundary
- The interface connecting SHN finding lifecycles to enterprise systems (Jira, ServiceNow, Splunk, DefectDojo).
- Standardized webhook and export adapter boundaries consuming normalized finding events.

# 10. Future Extensibility Boundaries

To ensure that future plugins cannot compromise system stability or security, SHN establishes clear **Extension Attachment Boundaries**:

```
+---------------------------------------------------------------------------------+
|                         PLUGIN EXTENSION BOUNDARIES                             |
+---------------------------------------------------------------------------------+
| ALLOWED EXTENSION ATTACHMENT POINTS    | FORBIDDEN ATTACHMENT POINTS (HARD CORE)|
+----------------------------------------+----------------------------------------+
| 1. Capability Providers (Tools/Scripts)| 1. Scope Enforcement Gatekeeper Core   |
| 2. Output Parsers & Normalizers        | 2. Authentication & Session Engine     |
| 3. Workflow Graph Templates            | 3. RBAC Policy Evaluator               |
| 4. Report Document Renderers           | 4. Relational Database Migration Engine|
| 5. Intelligence Model Connectors       | 5. Audit Log Ledger                    |
| 6. UI Dashboard Widgets & Panels       | 6. Task Dispatcher Authorizer          |
+---------------------------------------------------------------------------------+
```

Plugins may extend capabilities, parsing, workflows, reporting, models, and UI panels. Plugins **SHALL NOT** inject logic into scope enforcement, authentication, RBAC, database migrations, or the audit ledger.
