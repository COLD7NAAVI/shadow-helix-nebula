# Shadow : Helix Nebula (SHN)
## Phase 0.4: Architectural Principles & Invariants Specification

> **Authoritative Specification Notice**: This document establishes the binding, non-negotiable architectural principles, system invariants, forbidden patterns, and governance rules for Shadow : Helix Nebula (SHN). Built upon the product identity of Phase 0.1, the functional/non-functional requirements of Phase 0.2, and the domain boundaries of Phase 0.3, this specification acts as the permanent constitutional baseline for all subsequent design, database modeling, API development, worker implementation, and pull request reviews. Any code or configuration violating these invariants is architecturally invalid.

---

# 1. Introduction & Constitutional Purpose

### 1.1 Constitutional Role
In a long-lived, high-stakes cybersecurity platform, architectural drift, leaky abstractions, and premature coupling represent fatal failure modes. This document establishes the immutable architectural invariants of SHN. These rules are binding across all subsequent engineering phases:
- They govern all technical design documents (TDDs).
- They dictate database schemas, message broker topologies, and API contracts.
- They define the automated static linting rules enforced in continuous integration pipelines.
- They mandate strict rejection criteria during peer review and security audits.

### 1.2 Principle Formulation Standard
Every major principle within this specification is formulated using the rigorous reasoning pattern:
$$\text{WHAT} \longrightarrow \text{WHY} \longrightarrow \text{FUTURE IMPLICATION}$$

# 2. Foundational System Principles

### 2.1 Principle 1: Separation of Concerns & Clean Layering
- **WHAT**: System capabilities are strictly partitioned into discrete, orthogonal layers: presentation, coordination, task execution, data persistence, and cognitive assistance.
- **WHY**: Conflating workload execution with coordination or mixing domain rules into the presentation layer produces brittle code, prevents modular upgrades, and makes security auditing impossible.
- **FUTURE IMPLICATION**: Components can be refactored, scaled, or replaced without side effects rippling across unrelated subsystems.

### 2.2 Principle 2: Control, Execution, Data, Intelligence & Experience Layer Isolation
- **WHAT**: Each of the five core system layers operates behind strict interface boundaries and process perimeters.
- **WHY**: Security tools possess destructive capabilities; running untrusted scanners inside the central coordination process creates catastrophic stability and security vulnerabilities.
- **FUTURE IMPLICATION**: The Control Plane remains resilient and responsive even if an execution worker crashes, exhausts memory, or encounters a malicious target payload.

### 2.3 Principle 3: Capability-First vs. Provider Decoupling
- **WHAT**: Workflows, operators, and APIs interact exclusively with abstract capability intents (e.g., `capability:network.port-scan`) rather than concrete tool syntax (e.g., `nmap -sS`).
- **WHY**: Hardcoding specific CLI binaries or vendor flags makes workflows unportable, introduces tight coupling to underlying OS distributions, and prevents seamless tool upgrades.
- **FUTURE IMPLICATION**: Providers (Nmap, Masscan, RustScan) can be swapped, chained, or run in parallel consensus modes without modifying a single workflow definition.

### 2.4 Principle 4: Scope as a Mechanical Security Boundary
- **WHAT**: Scope is an enforceable programmatic barrier validated by an automated gatekeeper prior to task dispatch, rather than an informational documentation field.
- **WHY**: Accidental probing or scanning of out-of-scope assets causes legal liability, client contract breaches, and potential operational disruptions.
- **FUTURE IMPLICATION**: The platform deterministically prevents out-of-scope network traffic, eliminating human operator copy-paste errors and defending against DNS rebinding attacks.

### 2.5 Principle 5: Strict Authorization, Identity & Least Privilege
- **WHAT**: All actions, API invocations, and worker processes run under explicit identity tokens, granular RBAC policies, and dropped OS privileges.
- **WHY**: A security control plane handles sensitive access credentials and powerful offensive capabilities; over-privileged services create severe privilege escalation risks.
- **FUTURE IMPLICATION**: Worker compromise cannot lead to Control Plane takeover, and compromised operator credentials cannot exceed granted workspace permissions.

### 2.6 Principle 6: Multi-Tenant Workspace & Engagement Isolation
- **WHAT**: All operational assets, findings, evidence, workflows, and logs are logically segregated by Organization and Workspace boundaries.
- **WHY**: Security consultancies and enterprise teams manage multi-client environments where cross-tenant data leaks represent severe compliance and confidentiality violations.
- **FUTURE IMPLICATION**: Multi-client data residency is guaranteed at the database query planner level, enabling secure multi-tenant cloud deployments.

### 2.7 Principle 7: Evidence Immutability & Cryptographic Provenance
- **WHAT**: Raw tool outputs are captured unmodified, cryptographically hashed (SHA-256) upon ingestion, and linked to findings through an unbroken lineage graph.
- **WHY**: Unsubstantiated or tampered findings undermine client credibility, fail regulatory audits, and cannot withstand legal scrutiny in breach investigations.
- **FUTURE IMPLICATION**: Every finding in a generated report is backed by verifiable forensic proof, allowing third-party auditors to deterministically reproduce results.

### 2.8 Principle 8: Sovereign Operator Control & Mandatory Human Approval Gates
- **WHAT**: Automation and artificial intelligence operate strictly under human supervision; invasive or high-risk actions mandate explicit operator authorization.
- **WHY**: Fully autonomous security automation lacks real-world operational context, risks causing unintended service outages, and violates rules of engagement.
- **FUTURE IMPLICATION**: The platform empowers human operators with high-speed automation while preserving sovereign decision-making for destructive or high-risk actions.

### 2.9 Principle 9: Plugin Trust, Verification & Execution Sandboxing
- **WHAT**: Plugins must be cryptographically signed, declare explicit capability manifests, and execute within sandboxed container or process namespaces.
- **WHY**: The cybersecurity ecosystem moves rapidly, but third-party security tools and community scripts represent high-risk supply-chain attack vectors.
- **FUTURE IMPLICATION**: Operators can safely install community and proprietary plugins without risking host compromise or secret exfiltration.

### 2.10 Principle 10: Workflow Determinism, Cycle Bounding & Safety
- **WHAT**: Workflows are directed execution graphs supporting branches and loops, but all cycles must enforce mandatory, finite termination guards.
- **WHY**: Real-world security tradecraft requires iterative discovery, but unbounded loops cause infinite execution, worker starvation, and runaway cloud billing.
- **FUTURE IMPLICATION**: Complex multi-phase security assessments execute reliably, repeatedly, and terminate deterministically under all conditions.

### 2.11 Principle 11: API-First Architecture & Domain Core Independence
- **WHAT**: Every platform capability is designed as a versioned, public API before presentation interfaces are built; the domain core has zero knowledge of HTTP or UI code.
- **WHY**: Trapping business logic in web frontends prevents CLI scriptability, headless automation, and enterprise pipeline integrations.
- **FUTURE IMPLICATION**: Web, Desktop, CLI, and CI/CD pipelines enjoy $100\%$ feature parity, sharing the exact same underlying Control Plane APIs.

### 2.12 Principle 12: Deterministic, Verifiable & Reproducible Execution
- **WHAT**: An assessment step executed with identical target parameters, tool versions, and configuration inputs must produce verifiable, repeatable execution records.
- **WHY**: Remediating vulnerabilities requires re-testing under identical conditions to prove resolution to clients and compliance auditors.
- **FUTURE IMPLICATION**: One-click remediation verification allows teams to re-run historical workflows and compare results over time with precision.

### 2.13 Principle 13: Deep Full-Stack Observability & OpenTelemetry Tracing
- **WHAT**: All platform components emit structured JSON logs, Prometheus metrics, and OpenTelemetry distributed traces spanning from API call to child tool process.
- **WHY**: Distributed execution across multiple worker nodes becomes an opaque black box without correlated telemetry, crippling operational debugging.
- **FUTURE IMPLICATION**: Instant visibility into queue depths, worker resource bottlenecks, task latencies, and real-time streaming of execution stdout/stderr.

### 2.14 Principle 14: Blast Radius Minimization & Failure Isolation
- **WHAT**: Subsystems are engineered with circuit breakers, timeouts, and process boundaries such that the failure of any single component cannot cascade.
- **WHY**: Security tools routinely hang, run out of memory, segfault, or encounter defensive network tarpits.
- **FUTURE IMPLICATION**: A crashing scanner or timed-out network probe is isolated, logged, and cleaned up without impacting other running tasks or the Control Plane.

### 2.15 Principle 15: Core Decoupling & Frictionless Extensibility
- **WHAT**: The core platform provides extension points (capabilities, normalizers, workflows, report renderers, UI widgets) without requiring modifications to core repositories.
- **WHY**: Modifying core engine code to add support for a single new security tool creates technical debt and merge conflicts across teams.
- **FUTURE IMPLICATION**: Rapid ecosystem growth where internal red teams and community contributors author independent extensions.

### 2.16 Principle 16: Local-First / Distributed-Ready Topological Parity
- **WHAT**: The platform operates seamlessly on a single offline workstation while maintaining logical abstractions that allow it to scale across distributed cloud clusters.
- **WHY**: Security practitioners frequently operate in air-gapped test labs, client enclaves, or offline environments, yet enterprises require distributed scale.
- **FUTURE IMPLICATION**: Zero architectural rewrite required when transitioning an assessment from a local laptop to an enterprise multi-worker cluster.

### 2.17 Principle 17: Data Ownership, Lifecycle & Relational Integrity
- **WHAT**: Structured operational records reside in a relational database with strict foreign keys, while high-volume blobs reside in object storage; all entities enforce formal lifecycle states.
- **WHY**: Mixing multi-gigabyte PCAPs into relational databases degrades query performance, while loose unstructured files lack referential integrity.
- **FUTURE IMPLICATION**: Uncapped storage scalability for evidence artifacts while maintaining sub-millisecond relational query speeds for operational metadata.

### 2.18 Principle 18: Secure-by-Default Configuration & Hardened Posture
- **WHAT**: All default settings enforce maximum security: mandatory encryption, strict scope gatekeeping, unprivileged execution, and disabled auto-approval.
- **WHY**: Users rarely enable optional security settings; insecure defaults in a security platform present an unacceptable organizational liability.
- **FUTURE IMPLICATION**: Out-of-the-box compliance with stringent enterprise security baselines without requiring complex manual hardening.

### 2.19 Principle 19: Evolution, Contract Stability & Backward Compatibility Rules
- **WHAT**: APIs, plugin manifests, and workflow schemas adhere strictly to Semantic Versioning (SemVer); breaking schema changes require formal deprecation cycles.
- **WHY**: Breaking workflow schemas or plugin interfaces breaks historical assessment reproducibility and destabilizes automation pipelines.
- **FUTURE IMPLICATION**: Workflows authored today remain executable and auditable years into the future.

# 3. Canonical Architectural Invariants

The following twenty invariants constitute the binding constitutional laws of SHN. Every engineering implementation, database migration, API route, and worker module must satisfy these rules:

```
+---------------------------------------------------------------------------------------+
|                       CANONICAL ARCHITECTURAL INVARIANTS (INV)                        |
+---------------------------------------------------------------------------------------+
| INV-01: Control & Execution Plane Logical Separation                                 |
| INV-02: Presentation Layer Subordination (No UI Domain Logic)                         |
| INV-03: Capability Abstraction Primacy (Decoupled from Tools)                         |
| INV-04: Workflow Provider Independence (Decoupled from Vendors)                       |
| INV-05: Immutable Evidentiary Provenance (SHA-256 on Ingestion)                        |
| INV-06: Pre-Dispatch Mechanical Scope Gatekeeping                                     |
| INV-07: Non-Autonomous AI Containment (Zero Unsupervised Execution)                   |
| INV-08: Sandboxed Plugin Execution & Least Privilege                                  |
| INV-09: Infrastructure Neutrality of Domain Core                                      |
| INV-10: Local-First & Distributed Parity                                              |
| INV-11: PostgreSQL as Sole Authoritative System of Record                             |
| INV-12: Containers as Deployment Mechanism, Not Domain Architecture                  |
| INV-13: Asynchronous Task Dispatch & Isolation                                        |
| INV-14: Zero Direct Database Access for Execution Workers                            |
| INV-15: Mandatory Envelope Encryption for Secrets at Rest                             |
| INV-16: End-to-End Cryptographic Transit Security (TLS 1.3)                           |
| INV-17: Append-Only Immutable Audit Trail                                             |
| INV-18: Bounded Cyclic Graph Termination Invariant                                    |
| INV-19: Workspace Data Boundary Hermeticity                                           |
| INV-20: Mandatory Documented Decisions (ADR Discipline)                               |
+---------------------------------------------------------------------------------------+
```

### Detailed Invariant Specifications:

- **INV-01 (Control & Execution Separation)**: The Control Plane manages, coordinates, and persists state; it **SHALL NEVER** directly execute CLI binaries, security scripts, or untrusted workloads within its own process boundary.
- **INV-02 (Presentation Layer Subordination)**: The Experience Layer is strictly a presentation and interaction surface. Business logic, authorization rules, and scope checks **SHALL RESIDE EXCLUSIVELY** in the Control Plane API.
- **INV-03 (Capability Abstraction Primacy)**: Security capabilities are first-class abstract contracts. Domain entities and workflows **SHALL NOT** depend upon the syntax, flags, or binary names of concrete tool implementations.
- **INV-04 (Workflow Provider Independence)**: Workflow graphs define operational logic using abstract capability URIs. Workflows **SHALL NOT** be hardcoded to specific vendor tool providers.
- **INV-05 (Immutable Evidentiary Provenance)**: Every raw output, log, and artifact **SHALL** have its cryptographic SHA-256 hash computed immediately upon ingestion. Artifacts **SHALL NEVER** be modified or overwritten post-ingestion.
- **INV-06 (Pre-Dispatch Mechanical Scope Gatekeeping)**: The Task Orchestrator **SHALL** validate all resolved targets, CIDRs, domains, and capability actions against active scope boundaries prior to queue dispatch. Any out-of-scope task **SHALL** be rejected deterministically.
- **INV-07 (Non-Autonomous AI Containment)**: Artificial intelligence and cognitive models **SHALL NOT** possess direct execution authority. All model outputs **SHALL** be treated as untrusted advisory recommendations requiring human approval.
- **INV-08 (Sandboxed Plugin Execution & Least Privilege)**: Plugins **SHALL** execute in isolated containers or dropped-privilege namespaces with dropped Linux capabilities (`CAP_SYS_ADMIN` disabled) and read-only root filesystems.
- **INV-09 (Infrastructure Neutrality of Domain Core)**: Domain entities and application services **SHALL NOT** import concrete infrastructure drivers (e.g., direct SQL drivers, specific cloud SDKs). All storage and messaging interactions **SHALL** traverse abstract repository and queue interfaces.
- **INV-10 (Local-First & Distributed Parity)**: The platform **SHALL** be fully functional on a single offline workstation without internet access, while supporting scale-out across distributed worker nodes without core code modifications.
- **INV-11 (PostgreSQL as Sole Authoritative System of Record)**: PostgreSQL **SHALL** remain the single authoritative system of record for all relational state, finding data, scope definitions, and audit events.
- **INV-12 (Containers as Deployment Mechanism, Not Domain Architecture)**: Docker and OCI containers are deployment packaging and workload sandboxing mechanisms; core domain abstractions **SHALL NOT** depend on Docker-specific APIs.
- **INV-13 (Asynchronous Task Dispatch & Isolation)**: All execution workloads **SHALL** be dispatched asynchronously via decoupled queues. The Control Plane API **SHALL NEVER** block synchronously on external tool execution.
- **INV-14 (Zero Direct Database Access for Execution Workers)**: Execution workers **SHALL NOT** hold credentials to or directly connect to the primary PostgreSQL database. All state transitions **SHALL** be communicated via message queues or worker callback APIs.
- **INV-15 (Mandatory Envelope Encryption for Secrets at Rest)**: Target credentials, API keys, and sensitive tokens **SHALL** be encrypted at rest using AES-256-GCM envelope encryption with hardware or external key management.
- **INV-16 (End-to-End Cryptographic Transit Security)**: All internal and external network communications **SHALL** mandate TLS 1.3 encryption. Unencrypted HTTP or TCP communication is strictly prohibited.
- **INV-17 (Append-Only Immutable Audit Trail)**: Audit log tables **SHALL** be append-only. Database-level permissions **SHALL** deny `UPDATE` and `DELETE` operations on audit tables for all application roles.
- **INV-18 (Bounded Cyclic Graph Termination Invariant)**: Any workflow graph containing cycles or loops **SHALL** mandate an explicit, deterministic termination bound (maximum iteration count or timeout ceiling).
- **INV-19 (Workspace Data Boundary Hermeticity)**: All data persistence queries **SHALL** enforce `workspace_id` filtering. Cross-workspace data sharing without an explicit, audited administrative transfer is strictly prohibited.
- **INV-20 (Mandatory Documented Decisions)**: Any alteration to architectural invariants, core domain schemas, or infrastructure technologies **SHALL** require a formal, approved entry in the Architectural Decision Register (ADR).

# 4. Forbidden Architectural Dependencies & Anti-Patterns

To prevent structural degradation during implementation, the following architectural anti-patterns are **strictly prohibited**:

```
+---------------------------------------------------------------------------------------+
|                            STRICTLY FORBIDDEN PATTERNS                                |
+---------------------------------------------------------------------------------------+
| 1. The "Fat Frontend" Anti-Pattern:                                                   |
|    Placing authorization checks, scope validation, or finding correlation in the UI.   |
| 2. The "Worker Direct DB" Anti-Pattern:                                               |
|    Granting execution workers direct SQL connection strings to the primary database.   |
| 3. The "Tool-Locked Workflow" Anti-Pattern:                                           |
|    Writing workflow nodes that call `nmap` or `nuclei` directly instead of capability.|
| 4. The "Autonomous AI Agent" Anti-Pattern:                                            |
|    Granting an LLM or cognitive service direct API keys to dispatch scan tasks.        |
| 5. The "Blob-in-SQL" Anti-Pattern:                                                    |
|    Storing multi-gigabyte PCAPs, raw logs, or video artifacts directly in PostgreSQL.  |
| 6. The "Synchronous API Block" Anti-Pattern:                                          |
|    Holding an HTTP API request open while waiting for a 10-minute port scan to finish.|
| 7. The "Bypassed Scope Gate" Anti-Pattern:                                            |
|    Dispatching a task directly to a worker queue without pre-dispatch scope evaluation.|
| 8. The "Unhashed Evidence" Anti-Pattern:                                              |
|    Creating a finding linked to a loose raw output file without a SHA-256 hash.       |
| 9. The "Circular Context Import" Anti-Pattern:                                        |
|    Importing execution worker packages into domain core or orchestration packages.     |
| 10. The "Cloud-Only Hardcoding" Anti-Pattern:                                         |
|    Hardcoding AWS S3, Google Cloud, or Azure APIs directly into domain workflows.     |
+---------------------------------------------------------------------------------------+
```

# 5. Invariant Violation Handling & Governance Enforcement

### 5.1 Automated CI/CD Architectural Verification
In future implementation phases, these invariants will be enforced via automated mechanisms:
1. **Dependency Analysis Linters**: Static analysis tools (e.g., `arch-unit`, import linters) that automatically fail the build if a forbidden package import occurs (e.g., Worker importing Control Plane SQL models).
2. **Contract Validation Tests**: Automated API contract tests ensuring that public endpoints strictly match OpenAPI schemas without undocumented internal headers.
3. **Boundary Pen-Testing**: Automated security tests verifying that worker processes cannot reach the primary database port and that cross-workspace queries return zero records.

### 5.2 Remediation Protocol for Violations
If an invariant violation is detected in code or design:
1. **Immediate PR Rejection**: Any pull request introducing an invariant violation is blocked immediately.
2. **Architectural Review**: If an engineer believes an invariant must be modified, they must submit a formal ADR proposal justifying the change, documenting all trade-offs, and obtaining consensus from the lead software architect.
3. **Zero Silent Compromise**: Under no circumstances may an invariant be bypassed through undocumented workarounds or temporary flags.
