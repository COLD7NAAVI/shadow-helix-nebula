# Shadow : Helix Nebula (SHN)
## Phase 0.6: High-Level System Architecture Specification

> **Authoritative Specification Notice**: This document establishes the production-grade, high-level system architecture for Shadow : Helix Nebula (SHN). Integrating the foundational principles (0.1), requirements (0.2), domain boundaries (0.3), constitutional invariants (0.4), and traceability matrix (0.5), this specification details the physical and logical system topology, component interactions, trust perimeters, inter-process communication protocols, and execution lifecycles. It serves as the primary technical architecture blueprint for all subsequent domain and implementation phases.

# 3. Component Responsibilities & Boundary Interactions

### 3.1 Experience Layer Components
- **Public API Gateway**: Reverse proxy terminating TLS 1.3, validating JWT session tokens, enforcing global rate limits, and dispatching requests to Control Plane services.
- **Web UI Application**: Responsive single-page interface hosting visual workflow graph builders, live execution consoles, asset management tables, and report previewers.
- **Headless CLI Client**: Terminal-native binary interacting exclusively with the Public API Gateway; supports pipe-friendly JSON/YAML output modes for scripting.

### 3.2 Control Plane Core Services
- **Identity & RBAC Service (BC-IAM)**: Enforces multi-factor authentication, maps organizational roles to granular permissions, and manages cryptographic session tokens.
- **Workspace & Engagement Engine (BC-WKS)**: Manages logical client workspaces, engagement operational windows, asset inventories, and client metadata.
- **Scope Gatekeeper (BC-SCP)**: Intercepts all task generation requests; performs deterministic target resolution and validates IP/CIDR/Domain targets against authorized inclusions and exclusions prior to queue dispatch.
- **Capability & Plugin Registry (BC-CAP)**: Indexes abstract capabilities, validates cryptographic plugin signatures, verifies manifest schemas, and selects appropriate tool providers.
- **Workflow Graph Compiler (BC-WFO)**: Parses directed workflow graphs, validates cyclic loop bounds, resolves cross-node variables, and injects mandatory human approval gates before high-risk nodes.
- **Task Orchestrator (BC-EXE)**: Dispatches compiled task descriptors to Redis queues, tracks distributed execution state, monitors worker heartbeats, and manages task timeouts.
- **Normalization & Correlation Engine (BC-NRM)**: Ingests raw tool outputs via dedicated parsers, translates them into canonical domain schemas, and correlates multi-source observations against unified asset records.
- **Finding Lifecycle Manager (BC-FND)**: Manages vulnerability records through their formal state transitions (Draft $\rightarrow$ Under Review $\rightarrow$ Confirmed $\rightarrow$ Remediated), linking them to underlying evidence.
- **Evidence Vault & Provenance Ledger (BC-EVD)**: Ingests raw artifacts into object storage, computes SHA-256 hashes, and records unbroken execution lineage graphs.
- **Append-Only Audit Logger**: Emits structured, immutable audit log entries to PostgreSQL for every administrative and operational action.

### 3.3 Event & Queue Substrate
- **Task Dispatch Queues (Redis)**: High-speed, in-memory task queues providing reliable at-least-once delivery semantics for worker nodes.
- **Telemetry & Log Stream Bus (Redis Pub/Sub)**: Ephemeral event bus streaming real-time stdout/stderr chunks and execution progress bars to subscribed API gateways and WebSockets.
- **Dead-Letter Queue (DLQ)**: Quarantine queue capturing tasks that fail repeatedly or cause worker crashes, alerting operators for diagnostic review.

### 3.4 Execution Plane Subsystem
- **Execution Worker Daemon**: Dedicated background process running under an unprivileged OS account; polls the task queue over mTLS, initializes runtime sandboxes, executes tasks, and captures process outputs.
- **Runtime Adapters**:
  - *Local Process Runner*: Executes tools natively on host OS for lightweight development and local-first operation.
  - *OCI Container Runner*: Dispatches tools inside ephemeral Docker/Podman containers with isolated filesystems and dropped capabilities.
  - *Remote Enclave Runner*: Bridges execution to remote agent nodes positioned inside private target networks or cloud VPCs.

### 3.5 Data Plane Persistence Subsystem
- **PostgreSQL Database**: The authoritative ACID system of record storing users, workspaces, scope definitions, normalized assets, findings, lineage metadata, and audit logs.
- **Object Storage**: S3-compatible unstructured blob store housing multi-gigabyte raw tool outputs, network PCAPs, high-resolution screenshots, and compiled PDF deliverables.

### 3.6 Intelligence Layer Subsystem
- **Model Router**: Abstraction layer routing cognitive requests to external LLM APIs (OpenAI, Anthropic, Gemini) or local offline models (Ollama, vLLM).
- **Prompt Redaction Engine**: Deterministic filter removing target credentials, API tokens, and client PII before prompts leave the internal security boundary.
- **Human Approval Interlock**: Policy gate requiring an authenticated operator to review and approve AI-generated task recommendations before they can be compiled into active workflows.

# 4. Trust Boundaries & Security Perimeters

SHN partitions the platform into five distinct **Trust Zones** with strict cryptographic and network barriers:

```
+---------------------------------------------------------------------------------------+
| [TRUST ZONE 0: Untrusted External Environment]                                        |
| Public Internet Clients / External Web Browsers / CI/CD Pipelines                    |
+---------------------------------------------------------------------------------------+
                                           |  (Barrier 1: TLS 1.3 / OIDC / MFA / JWT)
                                           v
+---------------------------------------------------------------------------------------+
| [TRUST ZONE 1: Experience Layer & API Gateway]                                        |
| Reverse Proxy / Edge Router / Rate Limiting Filters                                   |
+---------------------------------------------------------------------------------------+
                                           |  (Barrier 2: Internal VPC / Strict Auth)
                                           v
+---------------------------------------------------------------------------------------+
| [TRUST ZONE 2: Control Plane Core (Highly Trusted)]                                   |
| Domain Logic / Database Access / Master Envelope Encryption Keys / Scope Enforcement  |
+---------------------------------------------------------------------------------------+
                                           |  (Barrier 3: Mutual TLS / Signed HMAC Tokens)
                                           v
+---------------------------------------------------------------------------------------+
| [TRUST ZONE 3: Execution Plane Worker Daemon (Moderately Trusted)]                    |
| Unprivileged Daemon / Zero Database Access / Dedicated Scratch Filesystem             |
+---------------------------------------------------------------------------------------+
                                           |  (Barrier 4: Sandbox / cgroups / Dropped Caps)
                                           v
+---------------------------------------------------------------------------------------+
| [TRUST ZONE 4: Sandboxed Tool Process (Untrusted / Hostile)]                          |
| Concrete Tool Binaries / Third-Party Scripts / Network Target Probes                  |
+---------------------------------------------------------------------------------------+
```

### 4.1 Zone Rules & Invariants
1. **Barrier 1 (Client $\rightarrow$ Gateway)**: All inbound traffic mandates TLS 1.3. Sessions require cryptographically verified JWTs following MFA/OIDC challenge.
2. **Barrier 2 (Gateway $\rightarrow$ Control Plane)**: Internal services reject requests lacking valid user security contexts.
3. **Barrier 3 (Control Plane $\rightarrow$ Worker Daemon)**: Workers connect via Mutual TLS (mTLS). Task descriptors must carry cryptographic HMAC signatures generated by the Control Plane.
4. **Barrier 4 (Worker $\rightarrow$ Tool Process)**: Tool processes execute with dropped Linux capabilities (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN` disabled), read-only root filesystems, and strict CPU/memory cgroups.
5. **Zero Database Credentials on Workers**: Execution workers hold **zero** credentials for PostgreSQL; direct SQL access from Zone 3 or Zone 4 is blocked at the network level.

# 8. Failure Domains & Blast Radius Isolation

To guarantee that individual tool errors, network timeouts, or hostile target responses cannot bring down the platform, SHN implements formal failure domain isolation:

### 8.1 Tool Process Failure Domain
- If a security tool binary crashes (e.g., segfault, memory exhaustion), the **Worker Daemon** intercepts the POSIX signal, captures the partial output, marks the task as `FAILED_PROCESS_CRASH`, releases resource locks, and reports the event to the Control Plane.
- Sibling tasks running on the same worker node are completely unaffected.

### 8.2 Network & Tarpit Failure Domain
- Hostile target networks deploying defensive tarpits (SYN cookies, slow HTTP responses) are bounded by strict **Task Execution Ceilings** and per-connection socket timeouts.
- When a task reaches its configured timeout ceiling, the worker issues `SIGTERM` followed by `SIGKILL` to the child process group, logs a `TASK_TIMEOUT` verdict, and returns control to the orchestrator.

### 8.3 Worker Node Failure Domain
- If an entire worker host experiences hardware failure or loses network connectivity, the Control Plane **Heartbeat Monitor** detects missing heartbeats within $\le 30\text{ seconds}$.
- Incomplete tasks are removed from the dead worker's lease, marked as eligible for retry, or transferred to the Dead-Letter Queue (DLQ).

### 8.4 Emergency Kill Switch
- The Control Plane provides an immediate **Emergency Stop API** that broadcasts cancellation signals across Redis Pub/Sub. All workers executing tasks within the specified workspace or engagement immediately abort running child processes within $\le 3\text{ seconds}$.

# 9. Architectural Invariants & Constraints Compliance

This high-level architecture strictly complies with the twenty canonical invariants defined in Phase 0.4:
- **INV-01 & INV-02**: Control Plane and Execution Plane are physically separate processes; the frontend operates strictly over public REST/WebSocket APIs without direct database access.
- **INV-03 & INV-04**: Capabilities are abstract contracts; workflows reference capability URIs rather than tool binary names.
- **INV-05 & INV-06**: Raw tool outputs are SHA-256 hashed immediately upon capture; tasks cannot reach the Redis dispatch queue without passing the pre-dispatch Scope Gatekeeper.
- **INV-07 & INV-08**: AI recommendations cannot execute without human approval; plugins execute inside sandboxed container/process runtimes with dropped privileges.
- **INV-10 & INV-11**: Local-first single-node deployment shares identical interfaces with distributed enterprise clusters; PostgreSQL remains the authoritative relational system of record.
- **INV-14**: Workers hold zero database credentials and interact strictly via task queues and signed callbacks.
